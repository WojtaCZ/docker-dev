# Unified dev container: design

Date: 2026-10-24. Repo: `docker-dev-template` (branch `unify-dev-container`).

## Intent

Today there are six repos: `docker-dev-template` (the base), and five children that
each add one platform on top of it: `embedded-base`, `embedded-arm`, `embedded-wch`,
`embedded-telink` and `web`. Real projects cross those boundaries. The motivating
case is firmware plus a PC control app plus that app's web interface. Switching
containers per sub-project is the problem.

Merge all five children into the template so there is **one image** that contains every
toolchain, debug tool and hardware-interface tool, ready at build time. Claude, working
inside it, picks the right tool for the project from context. No toolchain is ever
installed or built in a running container.

## Goals

1. **One image, everything baked at build time.** Common tools, ARM Cortex-M, WCH
   RISC-V, Telink (runtime parts), web, debug probes, serial/USB/logic-analyzer tools.
2. **Nothing lost in the merge.** Every package, binary, clone, env var, script, udev
   rule, MCP server, skill, command, doctor check and smoke-test assertion from the five
   children exists in the result. Appendix A is the inventory; a parity test enforces it.
3. **Context-driven tool selection.** Claude chooses the toolchain from where it is
   working (marker files such as `.mcu-profile.json`, `.web-profile.json`, a
   `CMakeLists.txt` that includes an ARM toolchain file) or from what the user says. The
   selection must not depend on a global mutable setting that one sub-project can break
   for another.
4. **Runtime device passthrough.** USB probes, boards, serial ports, HID, input and ALSA
   devices can be attached while the container runs, without restart, using the existing
   `dev-attach.sh` mechanism. Probes the container has never seen before work too.
5. **Trail-Code** (`github.com/trailhq/Trail-Code`, npm `@trailhq/trail-code`) is
   installed in the image and set up by Claude in every project it works in, including
   projects that combine firmware, software and web components.
6. **Claude memory persists across container re-runs** (`--rm` containers are the norm).

## Non-goals

- No installing or building toolchains inside a running container (the user's explicit
  rule). Per-project state (a `.mcu-profile.json`, Trail's `.trail/`) is not a toolchain
  and is created at runtime.
- No new Telink compiler distribution. The Telink SDK is EULA-restricted; it stays a
  host-mounted directory, exactly as in `embedded-telink`.
- No per-toolchain images, no image variants, no build-arg matrix.
- Not changing, deleting or archiving the five child repos in this work (see "Left to
  the user").
- No redesign of the `mcu`/`web` task runners beyond what selection needs.

## Anti-goals (a failure even if it builds)

- A tool that worked in a child quietly missing or behaving differently in the merged
  image.
- A project built with the wrong toolchain because a global env var (`CROSS_PREFIX`,
  `PATH` order) pointed somewhere else.
- A fresh attach of a probe requiring a container restart.
- Claude's always-loaded context (`~/.claude/CLAUDE.md`) ballooning with five platforms'
  reference text, so that every session pays for platforms it isn't using.
- Trail setup silently committing, pushing or sending project data anywhere.

## Sources

The five children are cloned at `~/Documents/docker-dev/docker-dev-<name>/`
(`embedded-arm`, `embedded-base`, `embedded-telink`, `embedded-wch`, `web`), next to the
template. **Where Appendix A and the repos disagree, the repos win.** Appendix A is a
summary written for review; the parity manifest is generated by scanning the actual
Dockerfiles, `COPY`d trees, skills, commands, udev rules and doctor checks, not by typing
in Appendix A.

## Constraints and facts found while reading the children

- Base distro is `archlinux:latest`. All children are `FROM` the template or
  `embedded-base`; `embedded-telink` branches straight off the template only to keep
  `lib32-glibc` out of the embedded base. In one image that reason disappears: enable
  `[multilib]` and install `lib32-glibc`/`lib32-gcc-libs` once.
- Only the Telink compiler is non-redistributable. Everything else is an Arch package,
  an official release tarball (xPack RISC-V GCC, `wlink`, `wchisp`) or a `git clone` with
  a pinned `ARG`.
- Tool name collisions are limited: each cross toolchain uses prefixed binaries
  (`arm-none-eabi-*`, `riscv-none-elf-*`, `tc32-elf-*`); host `gdb` is multiarch.
- **Real conflicts that need resolving (not just copying):**
  - `ENV CROSS_PREFIX` is set per child (`arm-none-eabi-`, `riscv-none-elf-`,
    `tc32-elf-`, empty in the base). Several shared skills read it. One image cannot
    have one value.
  - `/opt/embedded/profile.json` is a different default in arm, wch and telink. The
    telink one is a verbatim copy of the WCH one and is documented as wrong.
  - `~/.claude/CLAUDE.md` is assembled from numbered layers; each child's layer text
    assumes the other platforms are absent (telink's explicitly says the embedded layer is
    not there).
  - `entrypoint.sh` merges `~/.claude-layers/*.json` and concatenates
    `~/.claude-memory-layers/*.md`; the numbering (00/10/20) assumed a linear chain, and
    wch/arm/telink/web all claim 20.
  - `dev-up.sh` exists in four generations. arm's is the newest (live `/dev/bus/usb`,
    `/dev/input`, `/dev/snd` bind mounts, wildcard device-cgroup rules, hotplug `mknod`
    through `dev-attach.sh`, UID remap, git identity, SSH agent, extra group GIDs).
    wch and telink still enumerate `ttyACM`/`hidraw` once at start. web additionally
    joins the `docker-dev-web` network. The unified script is arm's, plus the pieces below.
  - arm's `dev-up.sh` grants device-cgroup rules for USB (189), hidraw, ttyACM, input,
    ALSA, but **not ttyUSB (major 188)**, and `dev-attach.sh` accepts `ttyUSB` nodes. The
    Telink profile defaults to `/dev/ttyUSB0`. In the unified script ttyUSB must be
    granted, otherwise the Telink flow breaks. Verify the major from `/proc/devices`, as
    the existing script does for the others.
  - `.devcontainer/devcontainer.json` in the children still uses the static
    `--device=/dev/bus/usb`; the hotplug approach lives only in `dev-up.sh`.
  - Claude project memory is keyed by working directory. Every project is mounted at
    `/workspace`, so every project shares one memory namespace inside the container.
- `entrypoint.sh` symlinks `~/.claude/projects`, `memory` from a host mount (devcontainer
  path) or `dev-up.sh` bind-mounts them directly. `~/.claude.json` and
  `.credentials.json` are bind-mounted onto their final paths on purpose (rename(2) onto
  a symlink orphans the host file). Keep that.
- Mounted, non-redistributable host tooling already supported and to be kept:
  `~/telink/Telink_825X_SDK` → `/opt/telink/sdk`, `~/st/STM32CubeCLT` → `/opt/st/clt`,
  `~/st/cubewba` → `/opt/st/cubewba`.
- Web ships DB *clients* plus `web/docker-compose.yml` with MariaDB, Postgres, Redis and
  Mailpit on the `docker-dev-web` network. That compose file is for backing services, not
  the dev container.
- Trail-Code facts (from its README): `npm i -g @trailhq/trail-code && trail init`;
  `init` writes nothing without a TTY unless given `--agents <ids>` or `--yes`; it
  creates `.trail/` (committed learnings), a `graft/` cache (git-ignored), `.claude/`
  skill/hook files, `.mcp.json`, `.gitignore`/`.ignore` edits, and reads the user's past
  Claude sessions for the repo and the last 50 merged-PR review comments (via `gh`).
  Personal learnings live in `~/.trail`. It sends anonymous usage stats unless
  `DO_NOT_TRACK=1` or `trail telemetry disable`. Monorepo support: one `.git` with
  workspace manifests (`package.json` workspaces, `go.mod`, `pyproject.toml`,
  `Cargo.toml`) gives per-scope ranking; submodules need `--follow-submodules`; nested
  repos need `--follow-nested-repos`; a folder of separate repos auto-splits with a
  `graft/workspace.json` index.

## Design

### 1. One image, one Dockerfile

`docker-dev-template` becomes the only image. Build order inside the Dockerfile puts the
rarely-changing, slowest layers first so editing one toolchain does not rebuild the rest:

1. Base: pacman rebuild-trust fix (`pacman-key --init/--populate`), full upgrade,
   template packages, `dev` user, Claude Code, superpowers plugin.
2. Shared embedded packages (everything from `embedded-base`), multilib enabled.
3. ARM: toolchain, multilib assertion, bench tools, CMSIS_6, CMSIS-DSP per core, ST
   device headers, STM32 SVD mirror.
4. RISC-V/WCH: xPack GCC, `wlink`, `wchisp`, `ch32fun`, `ch58x-sdk`.
5. Telink (runtime part only): lib32 packages, `TLSRPGM` clone, `/opt/telink` mount point.
6. Web: PHP stack, DB clients, nginx, deno, chromium, bun, PHP ini fixes.
7. Trail-Code (pinned version).
8. Scripts, udev rules, schemas, templates, doctor checks, Claude layers, skills.

Each step keeps the pinned-`ARG` convention and the "fail the build now" assertions from
the children (multilib `v8-m.main`, `wlink --version`, `wchisp config --help | grep
enable-debug`, `claude plugin list | grep superpowers`). Pinned versions stay exactly as
the children have them.

Image size will be large (low single-digit GB; chromium, CMSIS-DSP builds for five cores
and the 16 ST families dominate). That is accepted. The `ST_FAMILIES` and `DSP_CORES`
args remain so a slimmer build is possible, but the default builds everything.

### 2. Toolchain selection without global state

- **Remove the global `ENV CROSS_PREFIX`.** Toolchain choice becomes a property of the
  project, not the container.
- Each project component declares its toolchain through its existing profile:
  `.mcu-profile.json` gains a `crossPrefix` key (arm→`arm-none-eabi-`,
  wch→`riscv-none-elf-`, telink→`tc32-elf-`). The `mcu` runner exports `CROSS_PREFIX`
  from the profile for the command it runs and for `mcu --export`. Skills that need it
  outside `mcu` read it from the nearest `.mcu-profile.json`, or the baseline memory
  tells Claude how to look it up.
- `/opt/embedded/profile.json` is replaced by `/opt/embedded/profiles/{arm,wch,telink}.json`
  (alongside the existing `ch582f.json`). The scaffolding commands copy the right one.
  This also removes the "known-wrong telink profile" problem.
- `PATH` contains the union: `/usr/local/bin` symlinks for riscv (as in wch),
  pacman's ARM binaries, `/opt/telink/sdk/tools/tc32/bin` (harmless when not mounted),
  bun, `~/.local/bin`. No two toolchains export the same binary name, so order is not
  load-bearing. (To be verified by the parity test, which checks no duplicate basenames.)
- Context detection is done by Claude using marker files, written into the baseline
  memory as a short routing table (see §6). No daemon, no wrapper that guesses.
- A **project manifest is not introduced** for single-component repos. For multi-component
  repos (§4) a small optional `.dev-components.json` at the repo root lists
  `{path, kind}` entries (`kind` ∈ `fw-arm`, `fw-wch`, `fw-telink`, `web`, `desktop`,
  `other`) so Claude doesn't have to rediscover the layout every session. Claude creates
  it when scaffolding or when first asked to work on a multi-component repo, and the
  profiles inside each component stay the source of truth for build/flash commands.

### 3. Runtime device passthrough

One `scripts/dev-up.sh` (and `dev-up.ps1`), derived from the arm leaf's version, which is
the most complete, with these additions:

- Probes the container has never seen work without an allow-list: `/dev/bus/usb` is a
  live bind mount with a wildcard device-cgroup rule on major 189, so any USB probe
  reached through libusb works regardless of vendor/product ID. The udev attach rule
  matches device *classes* (any `ttyACM*`, `ttyUSB*`, `hidraw*`), not VID/PIDs, so it
  stays generic. Keyboards, storage and the like are not touched by it. The existing
  per-vendor udev rules only fix host-side permissions and stay as they are.
- ttyUSB cgroup rule (major from `/proc/devices`) so `dev-attach.sh` can attach
  `/dev/ttyUSB*`. `dev-up.sh`'s start-time mirror loop and the udev rule template
  (`90-dev-emb-attach.rules.in`) also cover `ttyUSB*`.
- Auto-detect and mount `~/telink/Telink_825X_SDK`, `~/st/STM32CubeCLT`, `~/st/cubewba`
  (the variables `DEV_TELINK_SDK`, `DEV_CUBECLT`, `DEV_CUBEWBA` keep their current names).
- Join the `docker-dev-web` network when it exists (web's behaviour).
- Single container name and image name (defaults `dev` / `dev-template`, overridable by
  `DEV_CONTAINER` / `DEV_IMAGE` as today). `dev-attach.sh` and the udev rule target
  that name.
- All existing env switches (`DEV_NO_BUILD`, `DEV_NO_PULL`, `DEV_REBUILD`,
  `DEV_NO_CACHE_VOLUMES`, `DEV_SKIP_UPDATE`, `DEV_DOCTOR`, `DEV_PROBE`, `DEV_CHANNEL`)
  keep working.
- Cache volumes: union of npm, uv, cargo, pyocd, ccache, plus composer and bun caches
  that web's flow benefits from.
- `.devcontainer/devcontainer.json` is brought up to the same passthrough behaviour
  (live bind mounts + cgroup rules instead of static `--device=/dev/bus/usb`) and the
  union of the VS Code extensions from the children (cortex-debug, peripheral viewer,
  clangd, cmake-tools and so on, plus the web ones web's devcontainer lists).
- `install-host-udev-rules.sh` ships the union of all udev rules (including wch's
  `61-wch-isp.rules` and arm's `90-dev-emb-attach.rules.in`), one copy, no per-leaf copies.
- `docker-compose.yml` (MariaDB, Postgres, Redis, Mailpit) is kept as an **optional**
  backing-services file under `compose/`. It is independent of the dev container.

### 4. Larger projects (firmware + desktop app + web)

Layouts Claude must handle, and what it does for each:

| Layout | Toolchain handling | Trail handling |
|---|---|---|
| One repo, components in subdirs | Each component dir has its own profile (`.mcu-profile.json`, `.web-profile.json`, and whatever the desktop app uses). `.dev-components.json` at root maps them. Claude runs `mcu`/`web` from the component dir. | `trail init` at the repo root. Add each component's manifest as a scope where Trail supports it (see below). |
| Folder of separate repos, no top-level `.git` | Same, per repo. | `trail build` at the parent (auto-splits, writes `graft/workspace.json`); `trail init` inside each child. |
| Superproject with submodules | Same. | `trail build --follow-submodules` from the root. |
| Nested clones (west/repo style) | Same. | `trail build --follow-nested-repos`. |

Trail's documented monorepo scopes are workspace manifests (`package.json` workspaces,
`go.mod`, `pyproject.toml`, `Cargo.toml`). A CMake firmware directory is not on that list.
The builder must check how Trail ranks a CMake component in a mixed repo and, if it is
not treated as its own scope, document the observed behaviour in the baseline memory so
Claude doesn't over-trust per-scope ranking there. This is a known unknown, not a design
decision.

The desktop app's own stack is not decided (see "Left to the user"). The design
reserves a `desktop` component kind and a place in the Dockerfile; it does not choose a
framework.

### 5. Trail-Code, set up in every project

- **Install:** `npm install -g @trailhq/trail-code` in the Dockerfile, version pinned by
  `ARG TRAIL_VERSION`. Global npm prefix must be writable at build time and executable by
  `dev`. A build-time check runs `trail --version`.
- **Setup per project, by Claude, deterministically:** a baseline `SessionStart` hook
  (declared in `claude-baseline/settings.json`) runs `trail-ensure`, a small script
  baked into the image:
  - not inside a git repo or workspace root → do nothing;
  - no `.trail/` → run `trail init --agents claude --yes` (the explicit flags are
    required because there is no TTY), then report what changed;
  - `.trail/` present → `trail build` to refresh the map if stale, nothing else;
  - detects the §4 layout and passes the matching `--follow-*` flag or builds at the
    parent.
- `/trail-setup` slash command and a baseline-memory rule so Claude can also do it on
  request and when the hook didn't (e.g. a new subdir added mid-session).
- **Never commits.** `trail init` leaves `.claude/`, `.mcp.json`, `.trail/`,
  `.gitignore`/`.ignore` changed in the working tree. Claude tells the user and leaves
  committing to them.
- **Persistence:** `~/.trail` (personal learnings) is bind-mounted from the host (or a
  named volume if the host dir doesn't exist) so it survives `--rm` containers. Repo
  learnings in `.trail/` are in the workspace and already persist. `graft/` is a
  rebuildable git-ignored cache in the workspace.
- **Telemetry:** the Dockerfile runs `trail telemetry disable` for the `dev` user, so
  Trail's anonymous usage ping is off by default. This is my call. It is deliberately
  **not** a global `DO_NOT_TRACK=1`, which would also silence unrelated tools' telemetry
  settings. The user can re-enable it with `trail telemetry enable`.
- **Auto-run and opt-out (my call):** the user asked for Trail in every project, so the
  hook runs by default. An empty `.no-trail` file in a repo, or `DEV_TRAIL=0` passed to
  `dev-up.sh`, makes `trail-ensure` do nothing. `trail-ensure` prints one line saying what
  it did so the setup is never silent.
- **Existing `.claude/` or `.mcp.json` (my call):** Trail's README says re-running only
  updates its own marker-fenced sections and its own files and never touches the rest.
  `trail-ensure` does not rely on that alone: after `init` it shows `git diff --stat` for
  files that were already tracked and tells the user which pre-existing files changed. It
  never resets or overwrites anything, and never fails the session.
- **Version pin (builder's task):** `TRAIL_VERSION` is set to the latest release at build
  time and recorded in the Dockerfile. The build checks that `trail init --help` lists
  `--agents` and `--yes`, and that `trail build --help` lists `--follow-submodules` and
  `--follow-nested-repos`, so a release without them fails the build instead of the hook.
- **Heads-up for the user, in the README:** `trail init` reads the user's past Claude
  sessions for that repo (using Claude under their login, counting toward usage) and the
  last 50 merged-PR review comments via `gh`. Both stay on the machine / go to Anthropic
  and GitHub only, per Trail's README.

### 6. Claude configuration (settings, memory, skills)

- **Settings:** one baseline layer is the union of MCP servers from the children:
  `github`, `git`, `context7`, `sequential-thinking` (template), `fetch` (de-duplicated;
  base and web both declared it), `playwright`, `sqlite` (web). Playwright's chromium
  path, `--no-sandbox`, and the `/workspace/.dev.db` sqlite path are kept as they are.
  `web-post-create.sh` (creates `.dev.db`) is called from `post-create.sh`.
  The numbered-layer mechanism in `entrypoint.sh` stays (it is how a user adds a private
  layer), but the image itself ships a single `00-baseline.json`.
- **Memory (`~/.claude/CLAUDE.md`):** kept deliberately **short**: an inventory of what is
  installed, the marker-file routing table ("`.mcu-profile.json` with an ARM chip → use
  `mcu`, `arm-none-eabi-*`…; `.web-profile.json` → use `web`…"), where mounted SDKs
  go, and the rules that apply everywhere (the `mcu`/`web` runners, never ad-hoc flash
  commands, `dev-doctor`, the Trail rule above). Platform detail (the ARM project layout
  tree, CMSIS-DSP usage, ch58x flow, Telink mount instructions) moves out of
  always-loaded memory into skills.
- **Skills:** all skills from all children are present (11 base + 12 ARM + 8 WCH + 2
  Telink + 5 web, plus commands `/probe-detect`, `/scaffold-mcu-project`,
  `/stm32-new-project`, `/ch32-new-project`, `/telink-sdk-check`). The children's own
  docs say flat `~/.claude/skills/<name>.md` files **do not trigger on their own**; only
  the directory form (`<name>/SKILL.md`) does. Because the goal is "Claude uses what it
  needs from context", flat skills are converted to directory form with a proper
  `description` frontmatter, content unchanged. The big platform sections of the old
  CLAUDE layers (ARM project layout, CMSIS-DSP, Telink mount, WCH CH58x) become new
  skills of the same style. `/scaffold-mcu-project <arm|wch|telink> <part>` copies from
  the new `profiles/` directory.
- **Doctor checks:** `30-embedded.sh`, `40-arm.sh`, `40-wch.sh`, `40-telink.sh`,
  `30-web.sh` all ship. A check for something that is a host mount (Telink SDK, CubeCLT,
  CubeWBA) reports "not mounted" as informational, not failure. Adds a Trail check
  (`trail --version`).

### 7. Claude memory persists across re-runs

- Keep the existing bind mounts (they are correct and were fixed with care):
  `~/.claude.json` and `~/.claude/.credentials.json` onto their final paths, `projects/`
  and `memory/` from the host `~/.claude`.
- Add persistence for the other per-user state Claude Code keeps that today dies with the
  `--rm` container and is not image-owned: session history, todos and plans (exact
  directory list to be verified against the installed Claude Code at build time, not
  assumed here). Image-owned content (`skills/`, `commands/`, `agents/`, `plugins/`,
  generated `CLAUDE.md` and `settings.json`) stays baked and is never mounted over.
- **Fix the shared-namespace problem:** mount the workspace at a stable, project-specific
  path instead of the fixed `/workspace`: `/workspaces/<project-dir-name>` with
  `WORKDIR` set to it (and a `/workspace` symlink kept for anything that hard-codes it).
  Claude's per-project memory is keyed by the working directory, so this gives each
  project its own memory instead of one shared pool. This is my call. Details, also my
  calls:
  - The directory name gets a short hash of the host path appended
    (`/workspaces/<name>-<hash>`), so two projects with the same folder name don't share
    a namespace again.
  - Existing memory keyed to `/workspace` (`projects/-workspace`) is left where it is and
    not migrated; new sessions start with the per-project key. Nothing is deleted.
  - Every hard-coded `/workspace` in the children is swept: the sqlite MCP path becomes
    relative to the working directory, `web-post-create.sh` and the task runners use
    `$PWD`, and `devcontainer.json` `workspaceFolder` follows the new mount. The
    `/workspace` symlink stays only as a fallback for third-party scripts.
- `~/.trail` persistence as in §5.

### 8. CI, tests, docs

- One `publish.yml` builds and pushes the single image under its **current name**,
  `ghcr.io/wojtacz/docker-dev-template`, with the same tag scheme, so `DEV_CHANNEL`
  (`latest`/`stable`) and `promote-stable.yml` keep working unchanged. The children's
  images simply stop being published; nothing existing is renamed. `DEV_IMAGE` defaults
  to `dev-template` (the local build tag).
  The leaf workflows disappear with their repos' build chain; the scheduled rebuild web
  had moves here.
- `tests/smoke.sh` is the union of the children's smoke tests, plus the new parity test
  and a check that exercises each toolchain by compiling a trivial program for each
  target (ARM Cortex-M33, RISC-V RV32EC, host C++), `trail --version`, and
  `web --list`.
- **Parity test** (`tests/merge-parity.sh`): driven by a checked-in manifest generated
  from Appendix A (package names, binaries, directories, env vars, scripts, udev rules,
  MCP servers, skills, commands, doctor checks). It fails if anything in the manifest is
  missing from the built image or the repo. This is how "did we merge everything" is
  answered with evidence instead of a review claim.
- READMEs and `WRITEUP.md` in the template are rewritten for the single image. The
  children's `WRITEUP.md` defect sections are read and any open defect that still applies
  is either fixed or carried over as a known issue.
- `sync-shared-assets.sh` and the telink drift check go away (there are no copies to
  drift).

## Is a single container an issue? (the user asked)

Not a blocker. Risks and how this design handles them:

| Risk | Handling |
|---|---|
| Toolchain conflicts | Prefixed binaries don't collide; `CROSS_PREFIX` is moved from a global env var to a per-project profile; duplicate-name check in the parity test. |
| Image size and build time | Accepted. Layer order puts slow-changing layers first; `ST_FAMILIES`/`DSP_CORES` args allow slim builds. |
| Always-loaded Claude context growing | Memory stays short; detail moves to auto-triggering skills. |
| Trail writes into every repo | It's the user's request; Claude never commits; documented. |
| Bigger blast radius (one container can reach all devices and all projects) | Same trust model as before (container is the boundary, `--dangerously-skip-permissions` is already the working mode per `mcu`'s security note); passthrough is still opt-in per `dev-up.sh` run. |

## Left to the builder

- Exact pacman/package de-duplication across Dockerfiles; layer ordering details.
- How `trail-ensure` detects a layout (any reasonable heuristic, documented in the
  script header); where `.dev-components.json` lives if Claude needs it elsewhere.
- Exact list of extra `~/.claude` subdirectories to persist (§7), verified against the
  installed Claude Code.
- The naming of new skills and the conversion mechanics for flat skills.
- Whether the CI scheduled rebuild keeps its current cadence.

## Left to the user (open)

1. **Desktop app stack.** Not decided: which framework or language the PC control app
   uses, whether it must run a GUI from inside the container (X11/Wayland forwarding),
   and whether it needs to build for Windows/macOS. This decides what, if anything,
   is added to the image for `desktop`.
2. **What "the compose script" is.** The repos start the dev container with
   `scripts/dev-up.sh`/`.ps1` (plain `docker run`) and only the web repo has a
   `docker-compose.yml` (backing services). This design assumes `dev-up.sh` is the
   launcher and the compose file is for services only. If the user has a different
   compose-based launcher, it needs to be matched.
3. **The five child repos.** After the merge, the user decides whether to archive them,
   delete them, or keep them. This work does not touch them or any remote.

## Appendix A: merge inventory (what must exist in the result)

**Template (kept):** base-devel, git, openssh, sudo, nodejs, npm, python, uv, which,
less, man-db, unzip, zip, curl, wget, jq, github-cli, util-linux; `dev` user and
sudoers; Claude Code installer; superpowers plugin; `entrypoint.sh`, `post-create.sh`,
